# HIVE Phase 2a (Projects) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give HIMARK a working project directory — create, browse, filter, favourite, and archive projects, each with a member list and role-based access — matching MVP.md Phase 2's "Projects" sub-scope and this plan's own spec.

**Architecture:** Same conventions Phase 1 established: RLS + a thin TypeScript service layer (client passed in, unit-testable), Server Actions for mutations, TanStack Query for client-side reads (this is the first plan to actually exercise it — Phase 1 wired the provider but never used it). One new piece Phase 1 didn't need: a `SECURITY DEFINER` RPC function for project creation, because RLS alone can't express "let a user insert the very first membership rows for a project they just created" without a bootstrapping mechanism.

**Tech Stack:** Same as Phase 1 — Next.js 16, TypeScript strict, Tailwind v4 + shadcn/ui (Base UI-backed, not Radix — see Phase 1's hard-won lessons below), Supabase, TanStack Query, Vitest + RTL, Playwright.

**Source spec:** `docs/superpowers/specs/2026-08-02-projects-design.md`.

**Lessons from Phase 1, carried forward as working assumptions — verify, don't re-litigate:**
- This project's shadcn primitives are **Base UI-backed, not Radix**. Any new primitive (this plan needs `AlertDialog`) may not support `asChild`, may use `onClick` instead of `onSelect`, and may defer open/close state via `requestAnimationFrame` (async in tests). Check the actual installed primitive's source before assuming Radix-style APIs.
- `tsx`/Vitest/Playwright do **not** auto-load `.env.local` — Phase 1 had to fix this repeatedly. Config for this is already in place (`vitest.config.ts`, `vitest.integration.config.ts`, `playwright.config.ts`); reuse it, don't recreate it.
- This repo's `eslint.config.mjs` has **no Prettier integration** — `npm run lint` passing does not mean Prettier is clean. Run `npx prettier --check` on every new/changed file before committing.
- Supabase embeds with more than one FK between the same two tables need an explicit disambiguation hint (`table!column(...)`) or PostgREST returns a parse-time ambiguity error that unit tests (which mock the client) cannot catch. `project_members` has two FKs to `users` (`user_id`, `added_by`) — the same shape as Phase 1's `workspace_members` bug. Any query embedding `project_members` with `users` must use the hint.

## Global Constraints

- TypeScript `strict` mode; zero ESLint/Prettier warnings before merge (run both, not just lint).
- Naming: components PascalCase, files kebab-case, functions camelCase, constants UPPER_SNAKE_CASE.
- Tailwind CSS + `styles/theme.css` tokens only — no raw hex, no arbitrary values.
- Database access only through the service layer (`services/`). Two carried-forward exceptions, both already established in Phase 1 for the identical pattern: (1) `create_project_with_owner`'s and `reassign_project_owner`'s compound operations live in `SECURITY DEFINER` Postgres functions precisely so the service layer doesn't need elevated client-side privileges to do them — the service layer calls these via `.rpc()`, never inserting into `project_members`/updating `projects.owner_id` directly for these operations; (2) test setup/teardown code in `tests/integration/` and `tests/e2e/` (Tasks 13-14) uses the admin client directly to create and clean up throwaway fixtures, per standard test-fixture practice — reviewers should not flag direct admin-client `.from(...)` calls in those files as a violation.
- `project_member_role` is exactly `project_owner` | `project_manager` | `contributor` | `viewer` — do not introduce FRS's flat role language here.
- `is_favourite` is workspace-wide (a single column on `projects`), not per-user — do not build a per-user favourites table.
- A project's Owner and its `project_members.role = 'project_owner'` row must never drift apart — exactly one project_owner at all times (see Task 4).
- A missing project and a project the requester can't access render the identical "not found" UI — never distinguish them, never surface a raw RLS/Postgres error.
- No CI/GitHub Actions (unchanged from Phase 1 — still no need for it this phase).

```sql
-- same pattern as Phase 1's is_workspace_member/is_workspace_admin)
create function can_create_project(target_workspace_id uuid, target_auth_user_id uuid)
returns boolean
language sql
security definer
set search_path = public
stable
as $$
  select exists (
    select 1
    from workspace_members wm
    join users u on u.id = wm.user_id
    where wm.workspace_id = target_workspace_id
      and u.auth_user_id = target_auth_user_id
      and wm.is_active = true
      and wm.role in ('owner', 'admin', 'member')
  );
$$;

create function is_project_member(target_project_id uuid, target_auth_user_id uuid)
returns boolean
language sql
security definer
set search_path = public
stable
as $$
  select exists (
    select 1
    from project_members pm
    join users u on u.id = pm.user_id
    where pm.project_id = target_project_id
      and u.auth_user_id = target_auth_user_id
  );
$$;

create function is_project_manager(target_project_id uuid, target_auth_user_id uuid)
returns boolean
language sql
security definer
set search_path = public
stable
as $$
  select exists (
    select 1
    from project_members pm
    join users u on u.id = pm.user_id
    where pm.project_id = target_project_id
      and u.auth_user_id = target_auth_user_id
      and pm.role in ('project_owner', 'project_manager')
  );
$$;

create function is_project_workspace_admin(target_project_id uuid, target_auth_user_id uuid)
returns boolean
language sql
security definer
set search_path = public
stable
as $$
  select exists (
    select 1
    from projects p
    join workspace_members wm on wm.workspace_id = p.workspace_id
    join users u on u.id = wm.user_id

alter table projects enable row level security;
alter table project_members enable row level security;

create policy "projects_select_member_or_workspace_admin"

  on project_members for select

create policy "project_members_write_manager_or_workspace_admin"
  on project_members for all
  using (is_project_manager(project_id, auth.uid()) or is_project_workspace_admin(project_id, auth.uid()))

-- Project creation RPC: RLS alone cannot express "let a user insert the very
-- first membership row(s) for a project that has zero members yet" (the
-- project_members write policy requires already being a manager, which is
-- impossible before any member row exists). This function does the whole
-- compound operation (insert project, insert initial membership rows) as
-- one atomic, elevated-privilege call -- but re-validates authorization
-- internally rather than trusting the caller, since SECURITY DEFINER
-- bypasses RLS by design.
create function create_project_with_owner(
  p_workspace_id uuid,
  p_name varchar,
  p_description text,
  p_status project_status,
  p_priority task_priority,
  p_owner_id uuid,
  p_start_date date,
  p_due_date date,
  p_member_ids uuid[]
)
returns projects
language plpgsql
security definer
set search_path = public
as $$
declare
  v_creator_id uuid;
  v_new_project projects;
  v_member_id uuid;
begin
  select id into v_creator_id from users where auth_user_id = auth.uid();
  if v_creator_id is null then
    raise exception 'Not authenticated';
  end if;

  if not can_create_project(p_workspace_id, auth.uid()) then
    raise exception 'You do not have permission to create a project in this workspace';
  end if;

  insert into projects (workspace_id, name, description, status, priority, owner_id, start_date, due_date, created_by)
  values (p_workspace_id, p_name, p_description, p_status, p_priority, p_owner_id, p_start_date, p_due_date, v_creator_id)
  returning * into v_new_project;

  insert into project_members (project_id, user_id, role, added_by)
  values (v_new_project.id, p_owner_id, 'project_owner', v_creator_id);

  if v_creator_id != p_owner_id then
    insert into project_members (project_id, user_id, role, added_by)
    values (v_new_project.id, v_creator_id, 'project_manager', v_creator_id);
  end if;

  if p_member_ids is not null then
    foreach v_member_id in array p_member_ids loop
      if v_member_id != p_owner_id and v_member_id != v_creator_id then
        insert into project_members (project_id, user_id, role, added_by)
        values (v_new_project.id, v_member_id, 'contributor', v_creator_id);
      end if;
    end loop;
  end if;

  return v_new_project;
end;
$$;

grant execute on function create_project_with_owner(uuid, varchar, text, project_status, task_priority, uuid, date, date, uuid[]) to authenticated;
```

```typescript
import type { SupabaseClient } from '@supabase/supabase-js'
import type { Database } from '@/types/database'
import type { Project, ProjectStatus } from '@/types/project'

export interface ListProjectsFilters {
  search?: string
  status?: ProjectStatus
  ownerId?: string
  favouritesOnly?: boolean
  sortBy?: 'name' | 'due_date' | 'created_at' | 'priority'
  sortDirection?: 'asc' | 'desc'
}

function mapProject(row: {
  id: string
  workspace_id: string
  name: string
  project_code: string
  description: string | null
  status: string
  priority: string
  owner_id: string
  start_date: string | null
  due_date: string | null
  completed_at: string | null
  progress_percentage: number
  is_favourite: boolean
  archived_at: string | null
}): Project {
  return {
    id: row.id,
    workspaceId: row.workspace_id,
    name: row.name,
    projectCode: row.project_code,
    description: row.description,
    status: row.status as Project['status'],
    priority: row.priority as Project['priority'],
    ownerId: row.owner_id,
    startDate: row.start_date,
    dueDate: row.due_date,
    completedAt: row.completed_at,
    progressPercentage: row.progress_percentage,
    isFavourite: row.is_favourite,
    archivedAt: row.archived_at,
  }
}

export async function listProjects(
  supabase: SupabaseClient<Database>,
  workspaceId: string,
  filters: ListProjectsFilters
): Promise<Project[]> {
  let query = supabase.from('projects').select('*').eq('workspace_id', workspaceId)

  if (filters.status) query = query.eq('status', filters.status)
  if (filters.ownerId) query = query.eq('owner_id', filters.ownerId)
  if (filters.favouritesOnly) query = query.eq('is_favourite', true)
  if (filters.search) query = query.ilike('name', `%${filters.search}%`)

  const { data, error } = await query.order(filters.sortBy ?? 'created_at', {
    ascending: filters.sortDirection !== 'desc',
  })

  if (error || !data) return []
  return data.map(mapProject)
}

export async function getProject(
  supabase: SupabaseClient<Database>,
  projectId: string
): Promise<Project | null> {
  const { data, error } = await supabase.from('projects').select('*').eq('id', projectId).single()
  if (error || !data) return null
  return mapProject(data)
}
```

- [ ] **Step 3: Add the `reassign_project_owner` RPC function**

`updateProjectMemberRole`'s owner-promotion path needs the same atomic, elevated-privilege treatment as project creation (a plain client-side update can't touch two rows across two tables — `projects.owner_id` and two `project_members` rows — as one guaranteed-consistent operation under RLS, since the caller's RLS-scoped update to `projects.owner_id` and the demote-previous-owner update are two separate statements that could partially fail). Create `supabase/migrations/0003_reassign_project_owner.sql`:

```sql
create function reassign_project_owner(p_project_id uuid, p_new_owner_user_id uuid)
returns void
language plpgsql
security definer
set search_path = public
as $$
declare
  v_caller_id uuid;
begin
  select id into v_caller_id from users where auth_user_id = auth.uid();
  if v_caller_id is null then
    raise exception 'Not authenticated';
  end if;

  if not (is_project_manager(p_project_id, auth.uid()) or is_project_workspace_admin(p_project_id, auth.uid())) then
    raise exception 'You do not have permission to reassign this project''s owner';
  end if;

  update projects set owner_id = p_new_owner_user_id, updated_at = now() where id = p_project_id;

  update project_members
    set role = 'project_manager', updated_at = now()
    where project_id = p_project_id and role = 'project_owner' and user_id != p_new_owner_user_id;

  update project_members
    set role = 'project_owner', updated_at = now()
    where project_id = p_project_id and user_id = p_new_owner_user_id;
end;
$$;

grant execute on function reassign_project_owner(uuid, uuid) to authenticated;
```

```typescript
import type { SupabaseClient } from '@supabase/supabase-js'
import type { Database } from '@/types/database'
import type { ProjectMember, ProjectMemberRole } from '@/types/project'

export async function listProjectMembers(
  supabase: SupabaseClient<Database>,
  projectId: string
): Promise<ProjectMember[]> {
  const { data, error } = await supabase
    .from('project_members')
    .select('id, project_id, user_id, role, user:users!user_id ( display_name, avatar_url )')
    .eq('project_id', projectId)

  if (error || !data) return []

  return data.map((row) => ({
    id: row.id,
    projectId: row.project_id,
    userId: row.user_id,
    role: row.role as ProjectMemberRole,
    displayName: row.user.display_name,
    avatarUrl: row.user.avatar_url,
  }))
}

export async function addProjectMemberByEmail(
  supabase: SupabaseClient<Database>,
  projectId: string,
  email: string,
  role: ProjectMemberRole,
  addedByUserId: string
): Promise<{ error: string | null }> {
  const { data: target, error: lookupError } = await supabase
    .from('users')
    .select('id')
    .eq('email', email)
    .single()

  if (lookupError || !target) return { error: 'No HIVE user found with that email.' }

  const { error } = await supabase
    .from('project_members')
    .insert({ project_id: projectId, user_id: target.id, role, added_by: addedByUserId })

  if (error) return { error: 'Could not add member. They may already be on this project.' }
  return { error: null }
}

export async function updateProjectMemberRole(
  supabase: SupabaseClient<Database>,
  projectId: string,
  userId: string,
  newRole: ProjectMemberRole
): Promise<{ error: string | null }> {
  if (newRole === 'project_owner') {
    const { error } = await supabase.rpc('reassign_project_owner', {
      p_project_id: projectId,
      p_new_owner_user_id: userId,
    })
    if (error) return { error: 'Could not reassign project owner.' }
    return { error: null }
  }

  const { error } = await supabase
    .from('project_members')
    .update({ role: newRole })
    .eq('project_id', projectId)
    .eq('user_id', userId)

  if (error) return { error: 'Could not update member role.' }
  return { error: null }
}

export async function removeProjectMember(
  supabase: SupabaseClient<Database>,
  projectId: string,
  userId: string
): Promise<{ error: string | null }> {
  const { error } = await supabase.from('project_members').delete().eq('project_id', projectId).eq('user_id', userId)

  if (error) return { error: 'Could not remove member.' }
  return { error: null }
}
```

```typescript
'use server'

import { revalidatePath } from 'next/cache'
import { createClient } from '@/lib/supabase/server'
import { updateProject, archiveProject, restoreProject } from '@/services/projects/project-service'
import type { Project } from '@/types/project'

export async function updateProjectAction(
  projectId: string,
  patch: Partial<Pick<Project, 'name' | 'description' | 'status' | 'priority' | 'startDate' | 'dueDate'>>
): Promise<{ error: string | null }> {
  const supabase = await createClient()
  const result = await updateProject(supabase, projectId, patch)
  if (!result.error) revalidatePath(`/dashboard/projects/${projectId}`)
  return result
}

export async function archiveProjectAction(projectId: string): Promise<{ error: string | null }> {
  const supabase = await createClient()
  const result = await archiveProject(supabase, projectId)
  if (!result.error) revalidatePath(`/dashboard/projects/${projectId}`)
  return result
}

export async function restoreProjectAction(projectId: string): Promise<{ error: string | null }> {
```

```tsx
const ROLE_LABELS: Record<ProjectMember['role'], string> = {
  project_owner: 'Project owner',
  project_manager: 'Project manager',
  contributor: 'Contributor',
  viewer: 'Viewer',
}

const ADDABLE_ROLES: ProjectMemberRole[] = ['project_manager', 'contributor', 'viewer']

export function ProjectMemberList({ projectId, members }: { projectId: string; members: ProjectMember[] }) {
  const router = useRouter()
  const [error, setError] = useState<string | null>(null)
  const [email, setEmail] = useState('')
  const [role, setRole] = useState<ProjectMemberRole>('contributor')
  const [isAdding, setIsAdding] = useState(false)

  async function handleRemove(userId: string) {
    const result = await removeProjectMemberAction(projectId, userId)
    if (result.error) {
      setError(result.error)
      return
    }
    router.refresh()
  }

  async function handleAdd() {
    setIsAdding(true)
    setError(null)
    const result = await addProjectMemberAction(projectId, email, role)
    setIsAdding(false)

    if (result.error) {
      setError(result.error)
      return
    }

    setEmail('')
    router.refresh()
  }

  return (
    <div className="space-y-4">
      {error && (
        <p role="alert" style={{ color: 'var(--danger)' }}>
          {error}
        </p>

        <div className="flex-1">
          <label htmlFor="add-member-email" className="text-sm">
            Email
          </label>
          <Input
            id="add-member-email"
            type="email"
            value={email}
            onChange={(e) => setEmail(e.target.value)}
            placeholder="teammate@himark.com"
          />
        </div>
        <select
          aria-label="Role"
          value={role}
          onChange={(e) => setRole(e.target.value as ProjectMemberRole)}
          className="h-9 rounded-md border px-2 text-sm"
          style={{ borderColor: 'var(--border-default)' }}
        >
          {ADDABLE_ROLES.map((r) => (
            <option key={r} value={r}>
              {ROLE_LABELS[r]}
            </option>
          ))}
        </select>
        <Button onClick={handleAdd} disabled={isAdding || !email}>
          {isAdding ? 'Adding…' : 'Add member'}
        </Button>
      </div>

      <div className="space-y-2">
        {members.map((member) => {
          const initials = member.displayName
            .split(' ')
            .map((part) => part[0])
            .join('')
            .slice(0, 2)
            .toUpperCase()

          return (
            <div key={member.id} className="flex items-center justify-between py-2">
              <div className="flex items-center gap-3">
                <Avatar>
                  <AvatarFallback>{initials}</AvatarFallback>

                  variant="ghost"
                  size="sm"
                  aria-label={`Remove ${member.displayName}`}
                  onClick={() => handleRemove(member.userId)}
                >
                  Remove
                </Button>
              )}
            </div>
          )
        })}
      </div>
    </div>
```

- **Spec coverage:** every section of `2026-08-02-projects-design.md` maps to a task — §5 (schema/RLS/RPC) → Task 1, ownership-reassignment rule → Task 4, §6.1 routes → Tasks 7-12, §6.3 components → Tasks 5-6, 8-12, §7 error handling → Tasks 8 (not-found), 7/9/11 (generic errors), 11 (archive confirmation), §8 testing → Tasks 2-4 (unit), 6-7/11-12 (component), 13 (RLS), 14 (e2e).
- **Type consistency:** `Project` and `ProjectMember` are defined once in Task 1 and imported everywhere else; `ListProjectsFilters` defined once in Task 2. `getProject` returning `Project | null` (not a discriminated union) is deliberate — Phase 1's 3-state union existed specifically to distinguish "not logged in" from "no membership," a distinction that doesn't apply here (the spec explicitly wants not-found and no-access collapsed into one state).
- **New risk this plan introduces beyond Phase 1's playbook, flagged for the implementer/reviewer:** the `create_project_with_owner` and `reassign_project_owner` RPC functions are new territory — Phase 1 never needed a callable-by-client SECURITY DEFINER function, only ones used internally by RLS policies. Task 1 and Task 4 both include explicit live-verification steps for this (confirming the `authenticated` grant actually works, not just that the function compiles) — whoever executes this should not skip those steps even under time pressure, since an RPC function that's correct SQL but not actually callable by the `authenticated` role would fail silently different from how a normal table insert fails.
- **Fixed during self-review:** the first draft of Task 4's `addProjectMember` took a `userId` and set `added_by: userId` — attributing every add to the person *being* added rather than the person performing the add, and Task 12's matching `addProjectMemberAction` was never actually called by `ProjectMemberList` (dead code, the same class of issue Phase 1's final review caught with `hooks/use-current-user.ts`). Fixed by: renaming to `addProjectMemberByEmail` (adding by email, resolved server-side to a `user_id`, since this plan doesn't build a workspace-member picker component), adding an explicit `addedByUserId` parameter resolved server-side in the Server Action via `getCurrentUserWithMembership` (never trusted from the client), and adding a real "add member" form to `ProjectMemberList` so the action is genuinely exercised. Test counts in Tasks 4 and 12 updated to match (7 and 5 respectively).
